# 4. Как реализовать три сложных места

Три подсистемы, где наивная реализация ломается на проде: уведомления, модерация доказательств и крипто-выплаты.

---

## 4.1. In-app уведомления

### Почему не «просто WebSocket»

Соблазн — держать сокет и пушить события. В Telegram Mini App это плохая идея: WebView агрессивно засыпает при сворачивании, соединение рвётся, а переподключение с восстановлением пропущенных событий — отдельная нетривиальная подсистема. Плюс сокет-сервер надо масштабировать и держать sticky-сессии.

Реальная потребность продукта: **счётчик непрочитанных обновляется в течение нескольких секунд**. Этого достаточно.

### Схема

```
Бизнес-событие (одобрение выполнения)
   │
   ├── в ОДНОЙ транзакции: смена статуса + запись в ledger
   │                        + Notification + OutboxEvent
   │
   ▼  COMMIT
outbox-worker  ──► создаёт NotificationDelivery по каналам
   │
   ├──► IN_APP: уже в БД, помечается SENT сразу
   └──► BOT: очередь bot-send с лимитером 30 msg/s
                 ретраи 1s → 5s → 30s → 5m
                 429 от Telegram → уважаем retry_after
                 403 (бот заблокирован) → users.botBlockedAt, SKIPPED
```

Ключевой момент — уведомление создаётся **в той же транзакции**, что и бизнес-изменение. Иначе получаем два класса багов: «статус изменился, а уведомления нет» и «уведомление пришло, а транзакция откатилась».

### Доставка на клиент

Три уровня, от простого к сложному:

1. **MVP — polling.** `GET /api/notifications/unread-count` каждые 20 секунд при активном приложении (останавливаем на `visibilitychange`). Плюс безусловная инвалидация после любого действия пользователя. Это ~3 запроса в минуту на активного пользователя — на десятках тысяч пользователей стоит копейки, а Redis-кэш счётчика на 10 секунд снимает нагрузку с Postgres почти полностью.
2. **Этап 2 — SSE.** `GET /api/notifications/stream` (`text/event-stream`) для мгновенной доставки. Одностороннего потока достаточно, и он переживает разрывы лучше сокета: браузер сам переподключается, а `Last-Event-ID` позволяет догнать пропущенное.
3. **Всегда — бот как «настоящий» push.** Telegram уже решил задачу пробуждения устройства. Дублируем в бот только `HIGH` и `CRITICAL`.

### Что дублировать в бот

| Событие | In-app | Бот |
|---|:---:|:---:|
| Задание одобрено | ✅ | ✅ |
| Задание отклонено | ✅ | ✅ |
| Нужна доработка | ✅ | ✅ |
| Выплата отправлена / завершена | ✅ | ✅ |
| Выплата не прошла | ✅ | ✅ |
| Аккаунт ограничен | ✅ | ✅ |
| Реферал заработал | ✅ | ✖️ (сворачиваем в дайджест) |
| Новый оффер | ✅ | ⚙️ по настройке |
| Пруф получен | ✅ | ✖️ |

Правило: в бот идёт то, из-за чего пользователь **должен вернуться в приложение или предпринять действие**. Всё остальное — только колокольчик, иначе бот превращается в спам и его блокируют, после чего мы теряем и важные сообщения.

### Группировка

`groupKey` сворачивает шум. Пять рефералов заработали за час — не пять уведомлений, а одно «Ваши рефералы принесли 340 ₽». Реализация: воркер с окном агрегации 15 минут по `groupKey`; при существующей непрочитанной записи с тем же ключом обновляем её, а не создаём новую.

### UI

- Колокольчик в хедере, бейдж с числом (99+ при переполнении).
- Список: непрочитанные визуально выделены, иконка по типу, относительное время («5 мин назад»).
- Тап → `deepLink` внутрь Mini App (`/tasks/{slug}`, `/profile/withdrawals/{id}`) + отметка прочтения.
- «Прочитать всё», группировка по дням, `haptic feedback` на новое уведомление.
- Оптимистичный апдейт счётчика, чтобы бейдж гас мгновенно.

## 4.2. Модерация доказательств

### Главная мысль

Модератор — узкое место всей экономики продукта. Если один модератор обрабатывает 40 выполнений в час вместо 240, вы платите в 6 раз больше за ту же пропускную способность и получаете нарушенный SLA, из-за которого пользователи уходят. Поэтому очередь модерации — **не CRUD-таблица, а специализированный инструмент**, и проектировать её надо как рабочее место оператора.

### Устройство очереди

**Приоритизация** (`ORDER BY`):
1. Нарушенный SLA (`reviewDeadlineAt < now()`) — всегда первые.
2. Высокий `riskScore` — требуют внимания человека.
3. Дорогие офферы.
4. FIFO по `submittedAt`.

**Лок выполнения.** При открытии карточки — `reviewerId` + `reviewLockedAt`, TTL 10 минут (Redis-ключ + поле в БД). Двое модераторов не смогут одновременно проверять одно выполнение. Истёкшие локи снимает воркер.

**Один экран, никакой навигации.** Слева пруфы, справа требования оффера и история пользователя. Решение → автоматически следующее выполнение в очереди. Модератор не должен возвращаться к списку.

**Горячие клавиши:** `A` — одобрить, `R` — отклонить, `V` — на доработку, `1..9` — быстрый выбор причины отказа, `←/→` — переключение пруфов, `Space` — зум. Отсюда и берётся требование к shadcn/ui и Radix — фокус-менеджмент и клавиатурная навигация из коробки.

### Что модератор видит рядом с пруфом

Контекст, без которого решение занимает минуту вместо десяти секунд:

- Требования оффера как чек-лист (что именно должно быть на скриншоте).
- Комментарий пользователя.
- История: одобрено/отклонено, `approvalRate`, `riskScore`, дата регистрации.
- **Флаги антифрода** с расшифровкой: «дубликат медиа — совпадает с выполнением TS-4F91 (phash, дистанция 3)».
- Предыдущие попытки по этому же офферу от этого пользователя.
- EXIF/метаданные (когда сделан скриншот, каким устройством).

### Автоматизация — три уровня фильтров до человека

Цель — чтобы человек смотрел только спорные случаи.

**Уровень 1. Валидация при отправке (мгновенно, без модератора):**
- обязательные типы пруфов присутствуют,
- MIME и размер файла,
- разрешение изображения не ниже минимума,
- длина комментария,
- дедупликация по `checksum` — отказ сразу, это тот же файл байт-в-байт.

**Уровень 2. Автоскоринг (воркер, до попадания в очередь):**
- перцептивный хэш → близкие дубликаты (расстояние Хэмминга ≤ 8),
- OCR по скриншоту → поиск обязательных маркеров (номер заказа, промокод, «Заявка одобрена»),
- проверка совпадения промокода из `offers.promoCode`,
- время между взятием и отправкой (2 секунды на «регистрацию в банке» — красный флаг),
- совпадение IP/устройства с другими аккаунтами,
- NSFW/скам-фильтр по медиа.

Результат — `riskScore` и `FraudFlag`. Скор не решает за человека, он **сортирует очередь и подсвечивает подозрительное**.

**Уровень 3. Автоодобрение (осторожно и только по совокупности):**

```
autoApprove = offer.autoApprove
           && user.approvalRate > 90%
           && user.tasksApproved >= 10
           && submission.riskScore < 20
           && (нет постбека ИЛИ постбек подтвердил конверсию)
```

Всегда оставляем случайную выборку 5 % автоодобренных на ручную проверку — иначе мы не узнаем, что правило начало пропускать фрод.

### Три исхода вместо двух

Бинарное «одобрить / отклонить» — источник негатива и потока в поддержку: пользователь честно выполнил задание, но приложил кривой скриншот, и получает отказ.

- **Одобрить** → `PENDING_PAYOUT`, начисление в `pending`, снятие холда по таймеру.
- **На доработку** (`NEEDS_REVISION`) → пользователь дозагружает пруфы, `revisionCount++`, задание не потеряно. Доступно только для причин с `allowsRevision = true`. Даёт дедлайн (например 24 часа), после которого `EXPIRED`.
- **Отклонить** → причина из справочника `rejection_reasons` + опциональный комментарий. Пользователь видит понятную формулировку, а не «отклонено». `riskPoints` из причины идут в `riskScore` пользователя.

Свободный текст в отказе — **опция, а не основной путь**: справочник причин даёт аналитику («40 % отказов — нечитаемый скриншот» → надо переписать инструкцию оффера) и предсказуемые формулировки без грубости.

### Защита от ошибок модератора

- Каждое решение → `SubmissionEvent` + `AuditLog`: кто, когда, почему.
- Окно отмены 60 секунд («Отменить» в тосте) — до фактического начисления.
- Ревью решений: выборка одобрений/отказов уходит на перепроверку старшему модератору.
- Метрики по модератору: скорость, доля отказов, доля оспоренных решений. Аномальная доля отказов у одного модератора — сигнал.
- Двойное подтверждение отказов по дорогим офферам (сверх порога суммы).

## 4.3. Выводы в крипту (USDT)

### Основной принцип

**Приватные ключи никогда не находятся в процессе, принимающем HTTP-запросы из интернета.** Это единственное архитектурное требование, отступление от которого нельзя компенсировать ничем.

```
API (интернет)  ──► withdrawals: PENDING_REVIEW   ключей нет
       │
       ▼
Финансист/автоправило ──► APPROVED
       │
       ▼
payout-worker (нет входящих портов) ──► Payout Signer ──► блокчейн
       │                                 ключи в KMS/HSM
       ▼
Вебхук подтверждений ──► SENT → COMPLETED
```

### Выбор способа отправки

Три варианта, и выбор зависит от объёма, а не от вкуса:

| Способ | Когда подходит | Риски |
|---|---|---|
| **Через биржу с payout API** (Bybit / OKX / Binance) | Старт, до нескольких сотен выплат в день | Зависимость от KYC биржи и её лимитов; аккаунт могут заморозить |
| **Кастодиальный провайдер** (Fireblocks, BitGo, Cryptomus, Coinbase Prime) | Средний объём, нужен комплаенс | Комиссии; всё равно внешняя зависимость |
| **Свой hot-кошелёк** (TRON/TON нода или Tatum/QuickNode) | Полный контроль, высокий объём | Вся ответственность за ключи и безопасность на нас |

**Рекомендация:** начать с провайдера/биржи (быстро, без своей инфраструктуры ключей), заложив слой абстракции `PayoutProvider` с методами `estimateFee`, `send`, `getStatus`. Тогда переход на свой кошелёк — это новый класс-адаптер, а не переписывание домена выплат.

### Сети

- **TRC-20 (TRON)** — основная. Копеечная комиссия, самая привычная сеть для USDT в СНГ.
- **TON** — вторая по приоритету: нативна для Telegram-аудитории, мгновенна, почти бесплатна.
- **ERC-20** — по запросу, с честным предупреждением о комиссии газа.

Адрес валидируется по формату и контрольной сумме **до** сохранения (TRON: base58check, начинается с `T`, 34 символа). Первая выплата на новый адрес — тестовая малая сумма при сумме сверх порога.

### Курс RUB → USDT

Баланс ведётся в рублях, выплата — в USDT. Значит нужен курс, и он источник споров.

- Источник: агрегат из 2–3 (Binance P2P медиана, биржевой спот, ЦБ как sanity-check).
- Обновление раз в 5 минут в `exchange_rates`.
- **Курс фиксируется в момент создания заявки** (`fxRate`, `fxLockedAt`) и показывается пользователю до подтверждения.
- Спред платформы (например 2 %) — в `app_settings`, отображается открыто.
- Защита от аномалий: отклонение нового курса > 10 % от предыдущего — заявки на крипто-вывод приостанавливаются, алерт админу. Это ловит и сбой источника, и реальный обвал рынка.

### Полный поток заявки

1. **Создание.** Проверки: `available >= amount`, минимальная сумма, суточный лимит, нет активной заявки, адрес в whitelist, пользователь не `LIMITED`.
2. **Холд в одной транзакции:** `Withdrawal(PENDING_REVIEW)` + `LedgerEntry(DEBIT, WITHDRAWAL_HOLD, idempotencyKey="withdrawal:{id}:hold")` + `available -= amount`, `hold += amount`. Средства заморожены сразу — иначе пользователь создаст десять заявок на один баланс.
3. **Антифрод-проверки:** возраст аккаунта, доля отказов, шаблон «набрал баланс за час», адрес, совпадающий с адресом другого пользователя.
4. **Одобрение.** Автоматически до порога (например 3000 ₽) при чистом профиле; вручную сверх порога. Свыше большого порога — второй аппрув другим сотрудником.
5. **Отправка.** `payout-worker` берёт заявку, `idempotencyKey` защищает от двойной отправки, вызывает Signer. Статус `PROCESSING` → получен `txHash` → `SENT`.
6. **Подтверждение.** Вебхук или поллинг ноды; `confirmations >= N` (TRON: 19 ≈ финальность) → `COMPLETED`, списание из `hold`, `LedgerEntry(WITHDRAWAL_SETTLED)`, уведомление с ссылкой на explorer.
7. **Ошибка.** `FAILED` → возврат: `LedgerEntry(CREDIT, WITHDRAWAL_REFUND)`, `hold -= amount`, `available += amount`, уведомление с причиной. Ретраи только для технических ошибок (нет связи с провайдером), но **никогда** после того как транзакция могла попасть в сеть — вместо этого ручной разбор.

### Идемпотентность (самое важное)

Двойная крипто-выплата необратима. Три барьера:

1. `withdrawals.idempotencyKey` UNIQUE — нельзя создать две заявки на одно действие.
2. `crypto_transactions(network, txHash)` UNIQUE — повторный вебхук не обработается дважды.
3. Перед отправкой воркер перепроверяет статус в БД внутри `SELECT ... FOR UPDATE`; если уже не `APPROVED` — выходит.

Плюс: `providerRef` (внешний ID запроса) отправляется провайдеру как ключ идемпотентности, чтобы двойной вызов API не превратился в две транзакции на его стороне.

### Операционная безопасность

- **Hot-кошелёк держит только суточную потребность.** Основные средства — на cold/warm, пополнение по расписанию вручную. Компромисс hot-кошелька тогда стоит одного дня выплат, а не всех средств.
- Whitelist адресов с задержкой активации нового адреса (24 часа) — ломает сценарий «угнали аккаунт, тут же вывели».
- Суточные лимиты: на пользователя и глобальный на платформу.
- Мониторинг баланса кошелька с алертом при опускании ниже порога.
- Ежедневная сверка: `SUM(completed withdrawals)` против фактических исходящих транзакций.
- Все действия с выплатами — в `withdrawal_events` и `audit_logs`, включая отказы.

### RUB-выплаты — отличия

Логика идентична, меняется только провайдер: карта (номер, валидация Луна, маска `•••• 4242`) или СБП (телефон + банк). Реквизиты шифруются AES-256-GCM, в открытом виде — только маска. В MVP отправка ручная с фиксацией референса платежа; далее — платёжный шлюз через тот же интерфейс `PayoutProvider`.
