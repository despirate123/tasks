# 1. Архитектура и стек

## 1.1. Ключевые ограничения, из которых вырастает архитектура

Прежде чем выбирать технологии, зафиксируем то, что реально диктует решения:

| Ограничение | Следствие для архитектуры |
|---|---|
| Mini App живёт внутри WebView Telegram | Никакого «своего» логина. Аутентификация — только через подпись `initData`. Мобильный WebView = жёсткие требования к весу бандла и TTI. |
| Пруфы — фото и видео | Файлы не должны идти через API-сервер. Только presigned-upload напрямую в S3. Иначе Node-процесс умрёт на первом же 50-мегабайтном видео. |
| Мы работаем с деньгами пользователей | Баланс нельзя хранить как изменяемое число. Только append-only леджер + денормализованный кэш. Все операции идемпотентны. |
| Модерация — ручная и массовая | Модератор — это узкое место продукта. Очередь модерации должна быть отдельным продуманным интерфейсом с горячими клавишами, а не «CRUD-табличкой». |
| 3 внешние сети офферов + ручное добавление | Нужен слой адаптеров с единым внутренним контрактом. Импорт **никогда** не перезаписывает то, что админ правил руками. |
| Выплаты в крипте | Приватные ключи не живут в том же процессе, что HTTP-сервер, принимающий запросы из интернета. |
| Уведомления в двух каналах (in-app + бот) | Одно событие → одна запись `Notification` → N записей `NotificationDelivery`. Публикация событий через transactional outbox. |

## 1.2. Стек

### Frontend (Mini App)

| Компонент | Выбор | Почему |
|---|---|---|
| Фреймворк | **Next.js 16 (App Router) + React 19 + TypeScript** | SSR/RSC даёт быстрый первый рендер в мобильном WebView — критично для Mini App. Один репозиторий на Mini App + админку + API. |
| Стили | **Tailwind CSS v4** | Совпадает с тем, как экспортируется Figma; нет рантайм-оверхеда CSS-in-JS. |
| UI-примитивы | **shadcn/ui (Radix)** | Доступность и клавиатурная навигация из коробки — это напрямую ускоряет очередь модерации. Код в репозитории, а не в `node_modules` — легко подогнать под макет. |
| Стейт сервера | **TanStack Query** | Кэш, инвалидация, оптимистичные апдейты, polling уведомлений — всё, что руками писать долго и больно. |
| Telegram SDK | **@telegram-apps/sdk-react** | Актуальный SDK: viewport, safe area, haptics, back button, `CloudStorage`, тема. |
| Формы | **react-hook-form + Zod** | Одна Zod-схема валидирует и на клиенте, и на сервере. |
| Графики | **Recharts** | Статистика рефералов и заработка. |

### Backend

| Компонент | Выбор | Почему |
|---|---|---|
| API | **Next.js Route Handlers + Server Actions** | На старте нет причин плодить сервисы. Общие типы и Zod-схемы с фронтом. Точки выделения в отдельный сервис описаны в §1.6. |
| БД | **PostgreSQL 16** | Транзакции, `NUMERIC` для денег, JSONB для метаданных, партиционирование леджера при росте. |
| ORM | **Prisma** | Типобезопасность, внятные миграции, `$transaction` с уровнями изоляции. |
| Кэш / очереди | **Redis 7 + BullMQ** | Отложенные задачи (снятие холда, автоодобрение, ретраи), rate limit, идемпотентность, ключи блокировок. |
| Файлы | **S3-совместимое (MinIO / Yandex Object Storage)** | Presigned PUT для загрузки, presigned GET со сроком жизни для модератора. Файлы никогда не публичны. |
| Бот | **grammY (отдельный Node-процесс)** | Лучший TS-DX для Telegram Bot API, встроенные `sequentialize` и лимитер. Отдельный процесс, чтобы webhook-нагрузка не конкурировала с рендером Mini App. |
| Воркеры | **BullMQ-воркеры (отдельный процесс)** | Синк офферов, доставка уведомлений, крипто-выплаты, пересчёт статистики. |
| Наблюдаемость | **Sentry + Pino (JSON-логи) + Prometheus/Grafana** | Обязательные алерты: очередь модерации > SLA, застрявшие выплаты, ошибки синка. |
| Валидация | **Zod** на каждой границе | Одна схема — один источник истины для типов. |

### Инфраструктура

- **Docker Compose** для локальной разработки (Postgres, Redis, MinIO, mailhog).
- **Продакшн:** контейнеры в managed-Kubernetes или на VPS через `docker compose` + Traefik/Caddy для TLS. Управляемый Postgres (Yandex Cloud / Neon / Supabase) — чтобы бэкапы и PITR не были нашей проблемой.
- **CI/CD:** GitHub Actions → lint + typecheck + tests + `prisma migrate deploy` → деплой.
- **Секреты:** Doppler / Vault / Yandex Lockbox. В репозитории — только `.env.example`.

## 1.4. Аутентификация

Одна точка входа — `POST /api/auth/telegram`:

1. Клиент передаёт `window.Telegram.WebApp.initData` (сырая строка).
2. Сервер проверяет HMAC-SHA256 подпись секретом бота (`WebAppData`) и что `auth_date` не старше 24 часов.
3. Пользователь создаётся или обновляется (`upsert` по `telegramId`); при первом входе применяется `start_param` как реферальный код.
4. Выдаётся пара JWT: access (15 минут, в памяти) и refresh (30 дней, httpOnly-cookie, `SameSite=None; Secure` — обязательно, иначе не работает в WebView).
5. Роль (`USER` / `MODERATOR` / `ADMIN` / …) кладётся в access-токен; каждый admin-эндпоинт перепроверяет роль в БД, а не доверяет токену.

**Админка** — это тот же Telegram-логин + роль в БД, плюс отдельный флаг допуска. Никаких паролей: пароли к деньгам — это лишний вектор атаки. Для чувствительных операций (выплата > лимита) — подтверждение через бот.

## 1.5. Модель денег

Правила, которые нельзя нарушать:

1. **`ledger_entries` — append-only.** Никаких `UPDATE`/`DELETE`; на уровне грантов Postgres роль приложения имеет только `INSERT` и `SELECT`. Ошибку исправляем записью типа `REVERSAL`.
2. **`wallets` — кэш.** `available`, `pending`, `hold` меняются только внутри той же транзакции, что и вставка в леджер. Ночная сверка сравнивает кэш с `SUM(ledger)` и алертит на расхождение.
3. **Каждая запись леджера имеет `idempotencyKey`** вида `submission:{id}:reward`, `withdrawal:{id}:hold`, `referral:{submissionId}:l1`. Уникальный индекс физически исключает двойное начисление.
4. **Три состояния денег:** `pending` (одобрено, в холде) → `available` (можно выводить) → `hold` (заморожено в активной заявке на вывод).
5. **Изоляция транзакций** — `Serializable` для операций со балансом, с ретраем при конфликте сериализации.

## 1.6. Когда пилить на сервисы

Начинаем монолитом — это осознанное решение, а не компромисс. Границы для будущего разделения уже прочерчены по модулям (`src/server/modules/*`), и выносить надо по конкретным триггерам:

| Триггер | Что выносим |
|---|---|
| > 5000 сообщений/мин в боте | Bot-gateway в отдельный сервис с очередью |
| Синк офферов начинает влиять на p95 API | Offer-sync в самостоятельный сервис-крон |
| Аудит требует изоляции контура выплат | **Payout-service выносим сразу в MVP** — единственный компонент, который изолирован с самого начала |
| Модерации нужен свой релизный цикл | Admin как отдельное приложение на том же API |

## 1.8. Безопасность

- Валидация `initData` на каждом запросе аутентификации; access-токен короткоживущий.
- Rate limit на Redis: взятие задания, отправка пруфов, создание заявки на вывод, upload-URL.
- Реквизиты выплат — AES-256-GCM, ключ в KMS. В открытом виде только маска.
- Пруфы в S3 не публичны: доступ только по presigned GET на 5 минут, и только для модератора и владельца.
- EXIF вырезается на воркере, оригинал сохраняется отдельно для арбитража.
- Полный аудит (`audit_logs`) на все админские действия — кто, что, когда, до/после.
- CSP с `frame-ancestors https://web.telegram.org`.
- Постбеки сетей — проверка подписи и allowlist IP.
- Крипто-выплаты: whitelist адресов, суточные лимиты, обязательный второй аппрув сверх порога.
