# 5. Техническое задание

**Проект:** ProfiBux — Telegram Mini App для выполнения рекламных заданий
**Версия:** 1.0
**Статус:** готово к передаче в разработку

---

## 5.1. Термины

| Термин | Значение |
|---|---|
| **Оффер / Задание** | Рекламное предложение, которое выполняет пользователь. Сущность `Offer` |
| **Выполнение** | Конкретная попытка пользователя выполнить оффер. Сущность `TaskSubmission` |
| **Пруф / Доказательство** | Фото, видео или текст, подтверждающий выполнение. `SubmissionProof` |
| **Холд** | Период между одобрением и доступностью денег к выводу |
| **Леджер** | Append-only журнал всех движений денег. `LedgerEntry` |
| **ETA одобрения** | Заявленное время проверки выполнения, `offers.approvalEtaMinutes` |
| **Сеть / Источник** | Партнёрская сеть-поставщик офферов: GetBlogger, Leadgid, Rafinad |
| **Постбек** | HTTP-callback от сети о состоянии конверсии |

---

## 5.2. Роли и права

| Роль | Права |
|---|---|
| `USER` | Выполнение заданий, вывод средств, рефералы |
| `SUPPORT` | Чтение профилей и выполнений, ответы в поддержку. Без доступа к деньгам |
| `MODERATOR` | Модерация выполнений, просмотр пруфов, отправка на доработку |
| `FINANCE` | Одобрение и обработка выплат, ручные корректировки баланса |
| `ADMIN` | Всё выше + управление офферами, пользователями, настройками |
| `OWNER` | Всё + управление ролями, доступ к настройкам интеграций и лимитам |

Доступ к админке — Telegram-логин + роль в БД. Роль проверяется на сервере на каждом запросе; клиентская проверка — только для UI.

## 5.3. Функциональные требования

### FR-1. Аутентификация

- **FR-1.1.** Вход исключительно через Telegram `initData` с проверкой HMAC-SHA256 подписи секретом бота. Невалидная подпись или `auth_date` старше 24 часов → `401`.
- **FR-1.2.** При первом входе создаётся `User`, генерируется уникальный `referralCode` (8 символов, base32 без похожих символов), создаётся `Wallet` в RUB, применяются дефолтные `NotificationPreference`.
- **FR-1.3.** `start_param` формата `ref_<code>` при первом входе привязывает реферала. Повторная привязка невозможна. Самореферал запрещён.
- **FR-1.4.** Access-токен JWT — 15 минут; refresh — 30 дней в httpOnly-cookie (`SameSite=None; Secure`).
- **FR-1.5.** Пользователь со статусом `BLOCKED` получает `403` с экраном-объяснением. `LIMITED` — может смотреть и выводить, но не брать новые задания.

### FR-2. Каталог заданий

- **FR-2.1.** Отображаются только офферы со `status = ACTIVE`, попадающие в окно `startsAt`/`endsAt`, доступные по гео/устройству/лимитам данного пользователя.
- **FR-2.2.** Фильтры: сложность (мультивыбор), категория, диапазон награды, «только доступные мне». Сортировка: по награде, по ETA одобрения, по новизне, по популярности. Поиск по названию и бренду.
- **FR-2.3.** Карточка в списке: иконка, название, бренд, награда, бейдж сложности, «≈ время одобрения», категория, метки «Хит»/«Новое».
- **FR-2.4.** Пагинация курсорная, по 20 элементов, бесконечная прокрутка.
- **FR-2.5.** Бейджи сложности: **Лёгкое** — зелёный, **Среднее** — жёлтый/янтарный, **Сложное** — красный.
- **FR-2.6.** ETA форматируется человекочитаемо: `< 60` → «≈ N мин»; `< 1440` → «≈ N ч»; иначе «≈ N дн».
- **FR-2.7.** Пустое состояние (фильтры ничего не дали) — с кнопкой сброса фильтров. Состояние загрузки — скелетоны. Ошибка — экран с повтором.

### FR-3. Карточка задания

- **FR-3.1.** Полное описание, пошаговая инструкция (`OfferStep` по порядку), награда, сложность, ETA, требования к пруфам, срок выполнения, остаток лимита.
- **FR-3.2.** Кнопка «Взять задание» создаёт `TaskSubmission` со статусом `DRAFT`, фиксирует `rewardAmount` (снапшот) и `expiresAt = now + completionTtlMins`.
- **FR-3.3.** Проверки при взятии (в транзакции): статус оффера, окно активности, `perUserLimit`, `totalLimit`, `dailyLimit`, гео, устройство, `newUsersOnly`, статус пользователя, отсутствие незавершённого выполнения по этому офферу. Отказ — с конкретной причиной, не «ошибка».
- **FR-3.4.** После взятия — таймер до `expiresAt` и переход к экрану отправки пруфов. Промокод (`offers.promoCode`), если есть, доступен для копирования в один тап.
- **FR-3.5.** Переход по `trackingUrl` открывается через `Telegram.WebApp.openLink` с подстановкой `clickId` (= id выполнения) в `sub_id`.

### FR-4. Отправка доказательств

- **FR-4.1.** Поддерживаются: фото (JPEG/PNG/WebP/HEIC, до 10 МБ, от 1 до `maxPhotos`), видео (MP4/MOV/WebM, до 100 МБ, до 120 с), текстовый комментарий (10–2000 символов).
- **FR-4.2.** Загрузка — presigned PUT напрямую в S3. Файл **не проходит** через API-сервер. `POST /api/uploads/presign` возвращает URL и `mediaId`.
- **FR-4.3.** Клиент сжимает изображения перед загрузкой (макс. 1920 px по длинной стороне, качество 0.85), показывает прогресс по каждому файлу и позволяет повторить упавшую загрузку.
- **FR-4.4.** Отправка (`POST /api/submissions/{id}/submit`) валидирует наличие всех обязательных типов пруфов согласно `requirePhoto` / `requireVideo` / `requireComment` / `minPhotos`. При нехватке — `422` с перечнем чего именно не хватает.
- **FR-4.5.** После отправки: `DRAFT → PENDING_REVIEW`, `submittedAt = now`, `reviewDeadlineAt = now + offer.approvalEtaMinutes`, создаётся уведомление `SUBMISSION_RECEIVED`, запускается задача автоскоринга.
- **FR-4.6.** В статусе `NEEDS_REVISION` пользователь может дозагрузить пруфы и отправить повторно; `revisionCount++`. Число доработок ограничено (по умолчанию 2).
- **FR-4.7.** Пользователь может отменить выполнение в статусах `DRAFT` и `NEEDS_REVISION` → `CANCELLED`.
- **FR-4.8.** Воркер переводит `DRAFT` с истёкшим `expiresAt` в `EXPIRED`.

### FR-5. Статусы выполнения

Основная цепочка: **ожидает подтверждения → ожидает выплаты → выплачено / отклонено**

| Статус | Отображение пользователю | Переходы |
|---|---|---|
| `DRAFT` | Черновик | → `PENDING_REVIEW`, `CANCELLED`, `EXPIRED` |
| `PENDING_REVIEW` | **Ожидает подтверждения** | → `IN_REVIEW`, `PENDING_PAYOUT`, `NEEDS_REVISION`, `REJECTED` |
| `IN_REVIEW` | Проверяется | → `PENDING_PAYOUT`, `NEEDS_REVISION`, `REJECTED`, `PENDING_REVIEW` (снятие лока) |
| `NEEDS_REVISION` | Нужна доработка | → `PENDING_REVIEW`, `EXPIRED`, `CANCELLED` |
| `PENDING_PAYOUT` | **Ожидает выплаты** | → `PAID` |
| `PAID` | **Выплачено** | терминальный |
| `REJECTED` | **Отклонено** | терминальный (возможен спор через поддержку) |
| `EXPIRED` | Истёк срок | терминальный |
| `CANCELLED` | Отменено | терминальный |

- **FR-5.1.** Каждый переход пишет `SubmissionEvent` с актором, статусами «из/в» и комментарием.
- **FR-5.2.** При одобрении: `PENDING_PAYOUT`, `payoutAvailableAt = now + offer.holdHours`, начисление в `wallet.pending`. При `holdHours = 0` воркер немедленно переводит в `PAID` и `pending → available`.
- **FR-5.3.** Экран «Мои задания»: табы «Активные» / «На проверке» / «Ожидают выплаты» / «Завершённые» / «Отклонённые», таймлайн по каждому выполнению, причина отказа явным текстом.

### FR-6. Профиль и баланс

- **FR-6.1.** Три числа явно и раздельно: **Доступно** (`available`), **В обработке** (`pending`), **В выводе** (`hold`). Пользователь должен понимать, почему баланс 5000, а вывести можно 3200.
- **FR-6.2.** История операций из `ledger_entries`: тип, сумма со знаком, дата, ссылка на связанную сущность, баланс после. Фильтр по типу и периоду, курсорная пагинация.
- **FR-6.3.** Статистика: выполнено заданий, заработано всего, выведено, процент одобрения, приглашено рефералов.
- **FR-6.4.** Реквизиты выплат: добавление, удаление (мягкое), выбор по умолчанию. Отображается только маска.

### FR-7. Вывод средств

- **FR-7.1.** Способы: карта РФ (RUB), СБП (RUB), USDT TRC-20, USDT TON, USDT ERC-20.
- **FR-7.2.** Минимальные суммы и комиссии — из `app_settings`, для каждого способа отдельно. Значения по умолчанию: карта — мин. 500 ₽, комиссия 0 %; USDT — мин. 1000 ₽, комиссия 2 %.
- **FR-7.3.** Перед подтверждением показывается расчёт: сумма списания, комиссия, к получению, для крипты — курс и сумма в USDT.
- **FR-7.4.** Курс фиксируется при создании заявки (`fxRate`, `fxLockedAt`), в интерфейсе — «курс действителен до HH:MM».
- **FR-7.5.** Проверки: `available >= amountGross`, минимальная сумма, суточный лимит, отсутствие активной заявки, валидность адреса/реквизитов, статус пользователя не `BLOCKED`.
- **FR-7.6.** Создание заявки атомарно: `Withdrawal(PENDING_REVIEW)` + `LedgerEntry(DEBIT, WITHDRAWAL_HOLD)` + `available -= gross`, `hold += gross`.
- **FR-7.7.** Пользователь может отменить заявку в статусе `PENDING_REVIEW` → возврат средств.
- **FR-7.8.** Статусы: `PENDING_REVIEW` → `APPROVED` → `PROCESSING` → `SENT` → `COMPLETED`; ветки `REJECTED`, `FAILED`, `CANCELLED` возвращают средства. Каждый переход — `WithdrawalEvent`.
- **FR-7.9.** Для крипты в завершённой заявке показывается `txHash` со ссылкой на explorer.

### FR-8. Уведомления

- **FR-8.1.** Колокольчик в хедере с бейджем непрочитанных (99+ при переполнении).
- **FR-8.2.** Список: иконка по типу, заголовок, текст, относительное время, выделение непрочитанных, группировка по дням, бесконечная прокрутка.
- **FR-8.3.** Тап → переход по `deepLink` + отметка прочтения. Кнопка «Прочитать всё».
- **FR-8.4.** Счётчик обновляется поллингом раз в 20 с при активном приложении (останов на `visibilitychange`) и инвалидируется после действий пользователя. На этапе 2 — SSE.
- **FR-8.5.** Уведомления с приоритетом `HIGH`/`CRITICAL` дублируются в бот согласно таблице §4.1.
- **FR-8.6.** Настройки уведомлений по типам, отдельно для in-app и бота (кроме `CRITICAL` — их отключить нельзя).
- **FR-8.7.** Тексты — из `NotificationTemplate`, редактируются в админке без релиза. Подстановка переменных `{{amount}}`, `{{offerTitle}}` и т.п.
- **FR-8.8.** При ошибке `403` от Telegram (бот заблокирован) — `users.botBlockedAt`, попытки прекращаются, in-app доставка продолжается.

### FR-9. Рефералы

- **FR-9.1.** Персональная ссылка `https://t.me/<bot>?start=ref_<code>`, кнопка «Поделиться» через Telegram share, QR-код.
- **FR-9.2.** Два уровня: L1 — 10 % от вознаграждения приглашённого, L2 — 3 %. Проценты в `referral_programs`, меняются админом.
- **FR-9.3.** Начисление реферального бонуса — в момент перехода выполнения в `PAID`, отдельной записью леджера с `idempotencyKey = referral:{submissionId}:l{level}`. Бонус платит платформа, у приглашённого не вычитается.
- **FR-9.4.** Реферал получает статус `ACTIVE` после первого оплаченного задания; до этого — `PENDING`.
- **FR-9.5.** Экран рефералов: заработано всего, приглашено, из них активных, список приглашённых (имя, дата, статус, принесено денег), график заработка по дням, история начислений.
- **FR-9.6.** Антифрод: самореферал запрещён; совпадение устройства/IP приглашающего и приглашённого → `FraudFlag` и удержание бонуса до ручной проверки.

### FR-10. Админ-панель: офферы

- **FR-10.1.** Список с фильтрами (источник, статус, категория, сложность), поиском и сортировкой. В строке видны: награда, сложность, ETA, статистика (взято/одобрено/отклонено), `approvalRate`, реальный ETA.
- **FR-10.2.** Создание и редактирование всех полей оффера, включая пошаговую инструкцию, требования к пруфам, лимиты, таргетинг, расписание.
- **FR-10.3. Ручное переопределение сложности.** Смена значения выставляет `difficultySource = MANUAL`. В UI — бейдж «вручную» и кнопка «вернуть авто» (возвращает `AUTO` и пересчитанное значение).
- **FR-10.4. Ручное переопределение ETA одобрения.** Аналогично через `approvalEtaSource`. Рядом отображается `actualEtaMinutes` (медиана факта) — чтобы админ видел расхождение с заявленным.
- **FR-10.5.** Синхронизация из сетей **никогда** не перезаписывает поля с `*Source = MANUAL`. После прогона — отчёт об изменениях.
- **FR-10.6.** Массовые действия: пауза, активация, архивирование, смена категории.
- **FR-10.7.** Действия «Дублировать» и «Предпросмотр как пользователь».
- **FR-10.8.** Любое изменение → `AuditLog` с `before`/`after`.

### FR-11. Админ-панель: модерация

- **FR-11.1.** Очередь с приоритизацией: нарушенный SLA → высокий `riskScore` → дорогие офферы → FIFO.
- **FR-11.2.** Фильтры: оффер, источник, статус, модератор, диапазон риска, «просроченные».
- **FR-11.3.** Лок выполнения за модератором на 10 минут при открытии; истёкшие локи снимает воркер.
- **FR-11.4.** Экран проверки: галерея пруфов с зумом, комментарий пользователя, требования оффера чек-листом, история и статистика пользователя, флаги антифрода с расшифровкой, предыдущие попытки.
- **FR-11.5.** Три действия: **Одобрить**, **Отклонить** (причина из справочника + комментарий), **На доработку** (только для причин с `allowsRevision`).
- **FR-11.6.** Горячие клавиши: `A` одобрить, `R` отклонить, `V` на доработку, `1..9` причина, `←/→` пруфы, `Space` зум. После решения — автоматический переход к следующему в очереди.
- **FR-11.7.** Окно отмены решения 60 секунд до фактического начисления.
- **FR-11.8.** Массовое одобрение выборки (с обязательным подтверждением и лимитом на размер пакета).
- **FR-11.9.** Метрики модератора: обработано за период, средняя скорость, доля отказов.

### FR-12. Админ-панель: выплаты

- **FR-12.1.** Очередь заявок с фильтрами по статусу, способу, сумме, дате. Сводка: сумма к выплате, число заявок, средний срок обработки.
- **FR-12.2.** Карточка заявки: пользователь, сумма/комиссия/к получению, реквизиты (раскрытие полных реквизитов — отдельным действием, пишется в `AuditLog`), результаты антифрод-проверок, история операций пользователя.
- **FR-12.3.** Действия: одобрить, отклонить (с причиной и возвратом средств), отметить отправленной (с вводом `txHash`/референса), пометить ошибкой.
- **FR-12.4.** Автоодобрение до порога суммы при чистом профиле; сверх большого порога — обязательный второй аппрув другим сотрудником.
- **FR-12.5.** Экспорт пакета заявок в CSV для ручной обработки и импорт результатов.
- **FR-12.6.** Все действия → `WithdrawalEvent` + `AuditLog`.

### FR-13. Админ-панель: пользователи и прочее

- **FR-13.1.** Поиск по Telegram ID, username, имени. Карточка: профиль, баланс, выполнения, выплаты, рефералы, устройства, флаги антифрода, полная история леджера.
- **FR-13.2.** Ручная корректировка баланса с **обязательным** комментарием → `LedgerEntry(MANUAL_ADJUSTMENT)`.
- **FR-13.3.** Смена статуса (`ACTIVE` / `LIMITED` / `BLOCKED`) с причиной и уведомлением пользователю.
- **FR-13.4.** Управление ролями — только для `OWNER`.
- **FR-13.5.** Справочники: категории, причины отказа, шаблоны уведомлений, правила антифрода, реферальные программы, `app_settings`.
- **FR-13.6.** Рассылки: фильтр аудитории, предпросмотр охвата, отложенный старт, статистика доставки.
- **FR-13.7.** Дашборд: на модерации / просрочено, заявок на выплату, DAU, выполнений за сутки, начислено/выплачено, топ офферов, воронка (взято → отправлено → одобрено → оплачено).

## 5.4. API

Базовый префикс `/api`. Аутентификация — `Authorization: Bearer <access>`. Ошибки — единый формат:

```json
{ "error": { "code": "INSUFFICIENT_BALANCE", "message": "Недостаточно средств", "details": {} } }
```

### Публичные / пользовательские

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/auth/telegram` | Вход по `initData`, выдача токенов |
| `POST` | `/auth/refresh` | Обновление access-токена |
| `GET` | `/me` | Профиль, баланс, роль, счётчик уведомлений |
| `GET` | `/offers` | Каталог. `?difficulty=&category=&minReward=&sort=&cursor=` |
| `GET` | `/offers/{slug}` | Карточка задания + доступность для пользователя |
| `POST` | `/offers/{id}/take` | Взять задание → `TaskSubmission(DRAFT)` |
| `GET` | `/submissions` | Мои выполнения. `?status=&cursor=` |
| `GET` | `/submissions/{id}` | Выполнение + пруфы + таймлайн |
| `POST` | `/uploads/presign` | Presigned PUT для S3 |
| `POST` | `/submissions/{id}/proofs` | Привязать загруженный медиафайл / текст |
| `DELETE` | `/submissions/{id}/proofs/{proofId}` | Удалить пруф (только в `DRAFT`/`NEEDS_REVISION`) |
| `POST` | `/submissions/{id}/submit` | Отправить на проверку |

## 5.7. Интеграции с сетями офферов

Единый внутренний контракт: адаптер каждой сети приводит внешние данные к `NormalizedOffer`.

```ts
interface NormalizedOffer {
  externalId: string;
  title: string;
  description: string;
  brandName?: string;
  iconUrl?: string;
  categoryHint?: string;
  networkPayout: Decimal;      // сколько платит сеть
  currency: string;
  geo: string[];
  device: DeviceRequirement;
  trackingUrl: string;
  steps: { title: string; description?: string }[];
  suggestedDifficulty?: Difficulty;    // если сеть отдаёт
  suggestedEtaMinutes?: number;
  raw: unknown;                 // сырой ответ для разбора спорных случаев
}
```

**Правила синхронизации:**
1. Идемпотентность по `(sourceId, externalId)` — `upsert`, а не вставка.
2. Поля с `*Source = MANUAL` **не перезаписываются никогда**.
3. Награда пользователю (`rewardAmount`) считается от `networkPayout` по правилу маржи из `app_settings` и требует подтверждения админом перед публикацией — цена для пользователя не должна меняться автоматически.
4. Новые офферы приходят в `status = DRAFT` и публикуются вручную.
5. Исчезнувший из выдачи сети оффер → `PAUSED` (не удаляется — на него есть история выполнений).
6. Каждый прогон → `OfferSyncRun` со счётчиками и отчётом об изменениях.
7. При недоступности API сети — экспоненциальный ретрай, затем алерт; каталог продолжает работать на последних данных.

## 5.10. Приёмка MVP

| № | Проверка |
|---|---|
| 1 | Вход только через валидный `initData`; подделанная подпись отклоняется |
| 2 | Каталог фильтруется по сложности, категории и награде; недоступные офферы не показываются |
| 3 | Взятие задания уважает все лимиты и таргетинг; отказ содержит внятную причину |
| 4 | Пруфы (фото + видео + текст) загружаются в S3 напрямую и привязываются к выполнению |
| 5 | Отправка без обязательного пруфа возвращает `422` с перечнем недостающего |
| 6 | Полная цепочка статусов проходится и отражается в таймлайне |
| 7 | Одобрение начисляет ровно один раз при повторных вызовах и параллельных запросах |
| 8 | Холд снимается воркером, `pending → available` |
| 9 | Заявка на вывод замораживает средства; отклонение возвращает их |
| 10 | Отклонение выплаты и повторное отклонение не удваивают возврат |
| 11 | Уведомления появляются в колокольчике; `HIGH`/`CRITICAL` дублируются в бот |
| 12 | Блокировка бота пользователем не ломает in-app доставку |
| 13 | Реферал привязывается по deep-link; бонус начисляется при `PAID` один раз |
| 14 | Админ меняет сложность и ETA; поля помечаются `MANUAL`; синк их не затирает |
| 15 | Очередь модерации приоритизирует просроченные и рискованные; лок работает |
| 16 | Все админские действия попадают в `audit_logs` с `before`/`after` |
| 17 | `SUM(ledger)` = `wallets.available` на любом объёме данных |
| 18 | Rate limit срабатывает на взятии задания, отправке и создании заявки на вывод |
| 19 | Пруфы недоступны по прямой ссылке без presigned-подписи |
| 20 | Приложение корректно работает в Telegram iOS, Android и Desktop, в светлой и тёмной теме |
